# FixFlow — Repair Shop Management System

> **FixFlow** — полноценная система управления ремонтными мастерскими, предназначенная для автоматизации приёма устройств, диагностики, ремонта, управления сотрудниками, складского учёта, финансовых операций и взаимодействия с клиентами.

**Тип проекта:** Desktop-приложение с клиент-серверной архитектурой  
**Язык разработки:** Java  
**Команда:** 3 разработчика  
**Основные пользователи:** владельцы ремонтных мастерских, администраторы и технические специалисты  
**Основная цель:** создать рабочий, расширяемый и демонстрируемый программный продукт, пригодный для университетской защиты и дальнейшего коммерческого развития.

---

# 1. Главная задача проекта

Необходимо разработать полноценное приложение FixFlow, которое заменяет разрозненные таблицы, бумажные записи и ручной учёт ремонтных заказов единой системой.

Приложение должно позволять управлять всеми основными процессами ремонтной мастерской:

- Регистрация клиентов и их устройств.
- Создание и сопровождение ремонтных заказов.
- Назначение сотрудников и контроль их работы.
- Диагностика неисправностей и ведение истории ремонта.
- Управление запчастями и складскими остатками.
- Учёт платежей, расходов и задолженностей.
- Управление гарантиями.
- Уведомления о важных событиях.
- Аналитика и финансовые отчёты.
- Просмотр статуса ремонта клиентом.
- Контроль действий пользователей и защита данных.

Это должен быть не демонстрационный макет, не набор статических экранов и не CRUD без бизнес-логики.

**Критически важное требование:** все основные действия пользователя должны работать с реальной базой данных через backend. Создание заказа, изменение статуса, списание деталей, регистрация платежа и формирование отчётов должны давать согласованный результат.

Необходимо реализовать полноценный сквозной сценарий работы мастерской, включая обработку ошибок, ограничения доступа и проверку бизнес-правил.

## Основные принципы

1. Desktop-клиент не подключается напрямую к PostgreSQL.
2. Все бизнес-операции выполняются на backend.
3. Все ограничения доступа проверяются сервером.
4. Контроллеры отвечают за HTTP, сервисы — за бизнес-логику, репозитории — за работу с данными.
5. Клиент получает данные через DTO, а не напрямую через JPA-сущности.
6. Денежные значения хранятся в `BigDecimal`.
7. Изменение нескольких связанных сущностей выполняется в одной транзакции.
8. Ошибки API имеют единый формат.
9. Статусы заказов и складские операции должны проходить серверную валидацию.
10. Приложение должно корректно сообщать об отсутствии соединения с сервером.
11. Долгие сетевые запросы не должны блокировать JavaFX Application Thread.
12. Секреты и пароли не хранятся в исходном коде.

- Просмотр журнала действий.
- Управление настройками мастерской.

## 4.2. MANAGER / ADMINISTRATOR

Администратор, работающий с клиентами и заказами.

Возможности:

- Регистрация клиентов и устройств.
- Создание ремонтных заказов.
- Назначение мастеров.
- Изменение допустимых статусов.
- Регистрация выдачи устройств.

- Регистрация платежей в рамках разрешённых операций.

- Создание и просмотр уведомлений.

Ограничения:

Технический специалист.

Возможности:

- Просмотр назначенных ему заказов.
- Просмотр необходимой информации об устройстве.
- Заполнение результатов диагностики.
- Добавление ремонтных заметок.
- Изменение статуса в пределах разрешённых переходов.
- Регистрация использованных деталей.
- Просмотр истории ремонта.
- Просмотр собственных задач и сроков выполнения.

Ограничения:

- Нет управления сотрудниками.
- Нет доступа к финансовым отчётам владельца.
- Нет возможности изменять роли.
- Нет произвольного изменения стоимости и платёжных записей.
- Нет удаления истории ремонта.

## 4.4. Принципы безопасности

- Пароли хранятся только в виде безопасных хешей.
- Не использовать открытые пароли в базе.
- Не выдавать всем пользователям административные права.
- Проверять права на каждом защищённом endpoint.
- Не полагаться на скрытие кнопок на frontend.
- Создать отдельную тестовую учётную запись для каждой роли.
- Не разрешать пользователю менять собственную роль.
- Не включать демонстрационные пароли в production-конфигурацию.
- Не возвращать пароли и хеши паролей через API.

Это центральная часть системы.

## 9.1. Данные ремонтного заказа

- ID.
- Уникальный номер заказа.
- Клиент.
- Устройство.
- Назначенный мастер.
- Сотрудник, принявший устройство.
- Описание проблемы.
- Результаты диагностики.
- Планируемые работы.

- Приоритет.
- Статус.
- Дата создания.
- Плановая дата завершения.
- Дата фактического завершения.
- Предварительная стоимость.
- Итоговая стоимость.
- Комментарии.
- Информация о гарантии.
- История статусов.

## 9.2. Статусы заказа

Используй перечисление `RepairOrderStatus`:

1. `RECEIVED` — устройство принято.
2. `DIAGNOSIS` — проводится диагностика.
3. `WAITING_FOR_APPROVAL` — требуется согласование стоимости.
4. `WAITING_FOR_PARTS` — ожидание запчастей.
5. `IN_REPAIR` — выполняется ремонт.
6. `TESTING` — проверка после ремонта.
7. `COMPLETED` — ремонт завершён.
8. `READY_FOR_PICKUP` — устройство готово к выдаче.
9. `DELIVERED` — устройство выдано клиенту.
10. `CANCELLED` — заказ отменён.

Переходы между статусами должны быть контролируемыми.

Например, нельзя выдать устройство, которое ещё находится на диагностике. Отмена заказа должна сопровождаться корректной обработкой резервов, использования запчастей и платежей.

## 9.3. Приоритеты

- LOW.
- NORMAL.
- HIGH.
- URGENT.

## 9.4. Функции

- Создание заказа.
- Редактирование разрешённых полей.
- Назначение мастера.
- Переназначение ответственного.
- Изменение статуса.
- Изменение приоритета.
- Добавление диагностических заметок.
- Регистрация работ.
- Регистрация использованных деталей.
- Просмотр истории статусов.
- Поиск по номеру заказа.
- Фильтрация по статусу, мастеру, периоду и приоритету.
- Просмотр просроченных заказов.
- Печать квитанции о приёме.
- Печать документа о выполненных работах.
- Закрытие заказа.
- Регистрация выдачи устройства.
- Создание гарантийной записи.

## 9.5. Бизнес-правила

- Номер заказа уникален.
- Заказ всегда связан с существующим клиентом и устройством.
- Устройство должно принадлежать указанному клиенту.
- Назначенный мастер должен быть активным сотрудником с соответствующей ролью.
- Изменения статусов сохраняются в истории.
- Финальная стоимость не может быть отрицательной.
- Нельзя списать отсутствующую деталь.
- Повторный запрос не должен приводить к двойному списанию запчастей.
- Выдача устройства требует завершённого ремонта или явно разрешённого исключения.
- Нельзя удалить заказ с историей операций обычным удалением записи.
- Операции закрытия должны корректно обрабатывать задолженности и возвраты.
- Все денежные расчёты выполняются через `BigDecimal`.

Не создавай финансовые записи, противоречащие статусу заказа или сумме оплаты.

## 21.9. Гарантии

Создай минимум 15 гарантийных записей:

- Действующие.
- Скоро истекающие.
- Истёкшие.

Все гарантии должны быть связаны с корректными ремонтными заказами и датами выдачи.

## 21.10. Уведомления и журнал аудита

Создай демонстрационные уведомления и записи аудита, отражающие различные операции пользователей.

В журнале должны быть примеры:

- Создания заказа.
- Изменения статуса.
- Назначения мастера.
- Использования запчастей.
- Регистрации платежа.
- Завершения ремонта.

## 21.11. Требования к seed-данным

1. Seed-данные должны создаваться автоматически в development-профиле.
2. Повторный запуск не должен дублировать записи.
3. Используй согласованные связи между сущностями.
4. Данные должны обеспечивать заполнение всех основных экранов.
5. Dashboard должен рассчитывать статистику на основании этих данных.
6. Моковые данные не должны автоматически добавляться в production.
7. Подготовь отдельный безопасный механизм очистки и повторного заполнения базы для локальной разработки.
8. Не смешивай создание структуры БД с бесконтрольной загрузкой тестовых данных.
9. Добавь документацию о том, как загрузить seed-данные вручную.
10. Предусмотри автоматические проверки целостности демонстрационных данных.

Для создания моковых данных допустимо использовать отдельный `CommandLineRunner`, специальный seed-сервис или другой документированный механизм. Он должен работать только при явно разрешённой конфигурации разработки.

Не запускай разрушительную очистку базы автоматически при каждом старте.

# 27. Демонстрационный сценарий

Система должна поддерживать следующий сквозной сценарий без ручного изменения базы данных.

1. Администратор входит в приложение.
2. Создаёт клиента.
3. Регистрирует его ноутбук.
4. Создаёт ремонтный заказ.
5. Назначает мастера.
6. Мастер входит под своей учётной записью.
7. Проводит диагностику.
8. Добавляет описание неисправности.
9. Меняет статус заказа.
10. Администратор регистрирует поступление необходимой запчасти.
11. Мастер добавляет запчасть в ремонтный заказ.
12. Складской остаток уменьшается ровно на использованное количество.
13. Мастер отмечает завершение ремонта.
14. Администратор регистрирует частичный или полный платёж.
15. Система корректно рассчитывает задолженность.
16. Устройство переводится в состояние готовности к выдаче.
17. Заказ закрывается после выдачи.
18. В истории сохраняются важные изменения.
19. Dashboard и отчёты отражают произошедшие операции.
20. Клиент может проверить статус по публичной ссылке, если этот интерфейс включён.

Если хотя бы один важный шаг не работает, основной пользовательский сценарий считается незавершённым.

Если объём проекта становится слишком большим, не удаляй основные бизнес-правила. Сначала заверши рабочий MVP, затем расширяй функциональность по этапам.

# 32. Финальная цель

В результате должен получиться полноценный Java-проект, демонстрирующий:

- Разработку backend на Spring Boot.
- Создание desktop-приложения на JavaFX.
- Проектирование реляционной базы данных.
- REST API.
- Авторизацию и ролевую модель.
- Бизнес-логику и транзакции.
- Складской и финансовый учёт.
- Автоматизированное тестирование.
- Интеграцию нескольких модулей.
- Работу в команде из трёх разработчиков.
- Подготовку продукта к демонстрации и потенциальному коммерческому использованию.

**Главный принцип:** лучше иметь меньше функций, полностью работающих в реальном приложении, чем множество экранов, которые только выглядят готовыми.

FixFlow должен запускаться, работать с PostgreSQL, содержать реалистичные демонстрационные данные и позволять преподавателю самостоятельно пройти основной сценарий использования.

# 33. Запуск текущей реализации

Исходные требования выше сохранены. Фактические результаты проверок и оставшиеся
ограничения указаны в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md).

## Windows: один запуск

Установите и откройте Docker Desktop с Linux containers / WSL 2, затем в обновлённой
папке проекта дважды нажмите **`start.cmd`**, либо выполните в PowerShell:

```powershell
.\start.cmd
```

Скрипт создаёт отсутствующий `.env`, собирает и запускает backend и PostgreSQL в Docker,
ждёт готовности, подготавливает JDK 21/Maven/библиотеки и открывает окно JavaFX в Windows.
При первом запуске дождитесь скачивания зависимостей. Вход: `owner@fixflow.test`,
пароль `Fictional-Demo-2026!`. Остановка: закрыть окно и выполнить **`stop.cmd`**;
том базы и существующий `.env` сохраняются. Подробности: [Windows](docs/windows.md).

Только серверы: `docker compose up -d --build --wait --wait-timeout 240`.
Эта команда запускает PostgreSQL и backend; графическое окно открывает `start.cmd`.
Внутри контейнера backend подключается к `postgres:5432`, наружу слушает localhost:8080
(либо `SERVER_PORT` из `.env`). Demo-данные создаются автоматически в dev-профиле.

## Linux, включая fish

В графическом сеансе Linux с JDK 21, GTK 3, Python 3, curl и работающим Docker Compose:

```bash
./start.sh
```

Скрипт создаёт отсутствующий `.env`, поднимает PostgreSQL/backend в Docker, ждёт их
готовности, скачивает Maven-зависимости и открывает JavaFX. `.cmd` предназначены для
Windows; `start.sh` запускается из fish через свой Bash shebang. Остановка серверов:
`./stop.sh`; том базы сохраняется. Только серверы: `./start.sh --services-only`.
Если backend уже запущен отдельно, откройте окно командой `./start.sh --desktop-only`;
адрес берётся из `FIXFLOW_API_URL` в `.env`. В этом режиме Docker не требуется.
Launcher читает настройки из `.env` как строковые значения, без выполнения команд.

## Подготовка

Требуются JDK 21, Docker с работающим daemon и Docker Compose. Для JavaFX нужен
графический сеанс; на Linux — GTK 3. Maven отдельно устанавливать не нужно.
Wrapper фиксирует Maven 3.9.16. Модули: contracts, backend, desktop.

```bash
cp .env.example .env
docker compose up -d --wait postgres
set -a
. ./.env
set +a
./mvnw -B -ntp verify
./mvnw -B -ntp -DskipTests install
```

`install` здесь только устанавливает уже проверенные JAR в локальный Maven-репозиторий,
чтобы отдельный запуск desktop разрешал contracts. Для полной повторной проверки
можно выполнить `./mvnw install` без пропуска тестов.

В первом терминале с загруженным `.env`:

```bash
java -jar fixflow-backend/target/fixflow-backend-0.1.0-SNAPSHOT.jar
```

Во втором терминале:

```bash
set -a
. ./.env
set +a
./mvnw -pl fixflow-desktop javafx:run
```

Альтернативные команды после сборки: `scripts/dev-start.sh db`, `backend`, `desktop`.
Остановка backend и desktop — закрытие окна или Ctrl+C в соответствующем терминале.
`docker compose stop postgres` останавливает БД с сохранением данных.

Backend слушает localhost:8080, PostgreSQL — localhost:5432. Порты и реквизиты задаются
через `.env`; приложение получает их как переменные окружения. Сам Spring Boot не
загружает `.env` автоматически. Адрес desktop задаётся `FIXFLOW_API_URL` или полем входа.

```bash
curl --fail http://127.0.0.1:8080/actuator/health
```

После успешного старта health возвращает `status: UP` и список групп проверок.
Flyway применяет V1–V6;
Hibernate проверяет схему и не изменяет её автоматически.

`.env.example` содержит только фиктивные локальные значения и явно включает профиль
`dev` и демонстрационные данные. [Учётные записи](docs/demo-accounts.md),
[архитектурные решения и финансовые формулы](docs/architecture.md),
[API](docs/api.md), [схема БД](docs/database.md),
[тестирование](docs/testing.md), [работа команды](docs/team-work.md).
Нельзя переносить демонстрационные реквизиты в production.

## Тесты и работа без Docker

По умолчанию интеграционные тесты сами запускают PostgreSQL 18.6 через Testcontainers.
Если daemon недоступен, можно предоставить отдельную PostgreSQL-базу для тестов:

```bash
export FIXFLOW_TEST_DATABASE_URL=jdbc:postgresql://127.0.0.1:55432/fixflow_test
export FIXFLOW_TEST_DATABASE_USER=fixflow
export FIXFLOW_TEST_DATABASE_PASSWORD=local_test_only
./mvnw -B -ntp verify
```

Тесты создают собственные записи в этой базе. Не указывайте рабочую пользовательскую БД.
Для отдельного локального кластера при установленном PostgreSQL:

```bash
mkdir -p .local
initdb -D .local/pgdata -U fixflow -A trust --encoding=UTF8
pg_ctl -D .local/pgdata -l .local/postgres.log -o "-h 127.0.0.1 -p 55432 -k $PWD/.local" start
createdb -h 127.0.0.1 -p 55432 -U fixflow fixflow_test
createdb -h 127.0.0.1 -p 55432 -U fixflow fixflow_demo
```

Это изолированный локальный кластер без реальных данных; для него в `.env` задайте
`POSTGRES_PORT=55432`, `POSTGRES_USER=fixflow`, `POSTGRES_DB=fixflow_demo`.
Он слушает только localhost. Остановить: `pg_ctl -D .local/pgdata stop`.

CI-конфигурация находится в `.github/workflows/verify.yml`; её наличие не означает,
что удалённый CI уже запускался. Профиль тестов не включает демонстрационный seed.

## Сценарий демонстрации

1. Войти менеджером, создать клиента, зарегистрировать устройство, принять заказ и назначить мастера.
2. Под мастером открыть назначенный заказ, начать диагностику, добавить результаты и перейти к согласованию.
3. Менеджером установить оценку и зафиксировать согласие клиента; при необходимости назначить цену работ.
4. Менеджером зарегистрировать поступление детали; мастером начать ремонт и использовать деталь.
5. Добавить выполненные работы; менеджер подтверждает их цены. Мастер переводит заказ на тестирование и завершает ремонт.
6. Менеджером принять частичную оплату, увидеть долг, проверить запрет выдачи до полного расчёта.
7. Принять остаток, перевести в готовность к выдаче, выдать устройство; проверить гарантию и историю.
8. Владельцем проверить склад, платежи, отчёты и аудит; сравнить Dashboard с проведёнными операциями.
9. Выдать tracking-ссылку, проверить безопасный JSON-статус без входа, отозвать ссылку и проверить отказ доступа.
10. При необходимости выгрузить CSV или отправить реальные квитанции на системный принтер.

Новая демонстрационная база без удаления предыдущих: остановить backend и выполнить
`scripts/dev-reset.sh --new-demo-database`, затем запустить backend снова.

## Проверка интерфейса

После запуска dev-backend и `./mvnw install` в графическом сеансе:

```bash
scripts/gui-smoke.sh
```

Сценарий открывает настоящий JavaFX под тремя ролями и создаёт собственные явно
помеченные записи GUI Smoke. Проверяет формы, назначение, диагностику, склад,
цену работы, оплату, отказ выдачи при долге, выдачу и гарантию. Чужие записи не удаляются.
Для headless CI этот дополнительный сценарий требует X11/виртуального дисплея;
обычный `verify` выполняет unit/HTTP/PostgreSQL-тесты без графического сеанса.

## Первый владелец без demo-данных

Для пустой установки с `SPRING_PROFILES_ACTIVE=prod` задайте через окружение
`FIXFLOW_BOOTSTRAP_OWNER_ENABLED=true`, `FIXFLOW_BOOTSTRAP_OWNER_EMAIL`,
`FIXFLOW_BOOTSTRAP_OWNER_NAME` и `FIXFLOW_BOOTSTRAP_OWNER_PASSWORD` (от 12 символов,
не более 72 байт UTF-8 — ограничение BCrypt).
Первый владелец создаётся только при пустой таблице пользователей. После инициализации
уберите bootstrap-флаг и пароль из окружения. Этот механизм не меняет существующие аккаунты.

В production demo-компоненты отключены даже при ошибочно включённом demo-флаге.
Cookie требует HTTPS; OpenAPI отключён, его можно явно включить `FIXFLOW_OPENAPI_ENABLED=true`.
TLS завершайте на доверенном reverse proxy; его развёртывание в репозиторий не входит.
Не включайте переменную `DEBUG` при обычном запуске Spring Boot: она повышает подробность логов.
Поддержка используемой ветки Boot и ограничения поставки описаны в архитектурном документе.
