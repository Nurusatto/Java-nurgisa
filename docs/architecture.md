# Принятые решения

- Один backend и PostgreSQL, три Maven-модуля. REST/JSON — единственный доступ desktop к данным.
- Java 21, Boot 3.5.16, OpenJFX 21.0.13, Maven 3.9.16. Flyway 11.20.3 выбран
  для PostgreSQL 18.6 вместо более старой версии BOM. Maven distribution проверяется SHA-256.
- Boot 3.5 завершил OSS-поддержку 25.06.2026. Перед коммерческим развёртыванием
  необходимо выбрать поддержку этой ветки или согласовать обновление основной версии.
- Spring Data JPA используется для аккаунтов/аутентификации. Прикладные команды и отчёты
  используют параметризованный JdbcTemplate; они участвуют в общей Spring-транзакции с JPA.
- DTO общих ошибок, пагинации и статусов находятся в contracts. Проекции предметных областей
  передаются как JSON-объекты; JPA-сущности и хеши паролей не сериализуются в API.
- Серверные сессии PostgreSQL, cookie только в памяти desktop, CSRF для изменений,
  BCrypt, проверка текущего состояния и роли сотрудника в БД на каждой бизнес-операции.
- Роли: OWNER, MANAGER, TECHNICIAN. Владелец не может изменить свою роль или отключить себя.
- PostgreSQL 18 с UTF-8 — базовая версия БД. Для регистронезависимого поиска используется
  встроенная Unicode-collation `pg_unicode_fast`, включая кластеры с locale C без ICU.
- Владельца устройства с историей менять нельзя. Состояние и комплектность фиксируются в заказе
  при каждом приёме: сохраняются отдельные снимки для повторных ремонтов одного устройства.
  Планируемая работа хранится в рекомендациях диагностики, выполненная — отдельными записями.
- Итог фиксируется при COMPLETED; принимаются частичные платежи после фиксации итога.
  Авансы до завершения не поддерживаются. Выдача требует нулевых долга и переплаты.
- Цена работ подтверждается менеджером; мастер не назначает произвольную цену.
  Действующие согласования должны покрывать итог. Цены деталей фиксируются при использовании.
- Склад без резервирования: использование списывает сразу. Пригодные детали возвращаются
  отдельной операцией. При отмене невозвратные детали остаются списанными только после
  явного подтверждения владельца. Отмена после технического завершения не допускается.
- Склад оценивается по средневзвешенной стоимости; возвраты используют исходную себестоимость.
  Последнее списание/возврат забирает остаток стоимости, сохраняя точность до копейки.
- Подтверждённые платежи и движения не удаляются. Возврат денег не меняет начисленную цену:
  для скидки используется отдельная корректировка. При необходимости после возврата возникает долг.
- Идемпотентные команды сохраняют ключ, SHA-256 запроса и ответ в той же транзакции.
- Публичный tracking предоставляет только JSON API, а не готовую клиентскую веб-страницу.
  256-битный случайный токен возвращается один раз; в БД остаётся SHA-256. Ссылки можно отозвать.
- Гарантия создаётся при выдаче, даты вычисляются в часовом поясе мастерской.
  Новое гарантийное обращение создаёт отдельный заказ, сохраняя историю исходного.
  Если прежний мастер отключён или сменил роль, новый заказ остаётся без назначения
  до выбора активного мастера администратором.
  Валюта блокируется после появления денежных операций, часовой пояс — после гарантий.
- Внешних SMS, банковского эквайринга и платных интеграций нет. Платёж регистрирует сотрудник.
- CSV формируется по реальным данным. Печатные формы используют JavaFX PrinterJob;
  встроенного генератора PDF нет, допускается системный PDF-принтер.

## Финансовые формулы

Начислено = final_total + корректировки. Оплачено = платежи − возвраты.
Долг = max(начислено − оплачено, 0), к возврату = max(оплачено − начислено, 0).

Выручка периода = первоначальные итоги заказов, выданных за период, плюс корректировки
уже выданных заказов, проведённые за период. Себестоимость = стоимость использованных
деталей этих выданных заказов за вычетом их складских возвратов.
Валовая прибыль = выручка − себестоимость. Операционный результат дополнительно вычитает
денежные расходы категорий, кроме PARTS_PURCHASE. Денежный поток = платежи − возвраты − все расходы.
Закупка на склад не вычитается из прибыли повторно вместе с себестоимостью ремонта.
Средний чек = выручка периода / число выдач; при отсутствии выдач отображается 0.
Месячные строки используют ту же модель событий: платежи, возвраты, выдачи, корректировки
и расходы учитываются по дате своего события в часовом поясе мастерской.
Корректировки не распределяются по видам работ: они отражаются в общей выручке отдельно.

## Неоднозначности требований и выбранные правила

| Требование | Принятое решение |
| --- | --- |
| ADMIN / OWNER и MANAGER / ADMINISTRATOR названы по-разному | Три роли OWNER, MANAGER, TECHNICIAN; администратор приёма — MANAGER |
| Завершение работ, готовность и выдача перечислены отдельно | COMPLETED фиксирует цену, READY_FOR_PICKUP разрешает выдачу, DELIVERED означает фактическую передачу; денежный расчёт проверяется при выдаче |
| Выручка по завершённому ремонту и поступившие платежи | Момент реализации для выручки — выдача; платежи отражаются независимо по дате; формулы приведены выше |
| Функции мастера и контроль финансов | Мастер фиксирует работы, менеджер подтверждает цену; завершение требует согласования и подтверждённых цен |
| Состояние/комплектность упомянуты у устройства | Они хранятся в каждом заказе как неизменяемый снимок конкретного приёма |
| Автоматический dev-seed и запрет demo в production | Требуются dev, отсутствие prod и явный demo-флаг; отдельный bootstrap OWNER для пустой production-базы |
| Публичная страница при desktop-клиенте | Безопасный HTTP/JSON endpoint; готовая публичная веб-страница не заявляется |
| PDF и ежедневная печать | Реальные CSV и PrinterJob; самостоятельный PDF-генератор отложен согласно разрешению README |

## Порядок реализации и вертикальный срез

1. Parent/contracts/backend/desktop, PostgreSQL, миграции, health и окно JavaFX.
2. Сессия и роли, клиент/устройство, приём/назначение и карточка заказа в интерфейсе.
3. Диагностика → согласование → ремонт → тестирование, с серверной политикой статусов.
4. Складская деталь и её стоимость → фиксация итога → частичная оплата → выдача/гарантия.
5. Закупки, контролируемые возвраты/отмена, гарантийные обращения, отчёты/уведомления/tracking.
6. Полный согласованный seed, регрессионные проверки, реальный GUI-сценарий и инструкции.

Минимальный рабочий вертикальный срез — клиент и устройство → заказ → диагностика и
согласование → одна работа и деталь → тестирование → итог → оплата → выдача с гарантией.
Этот срез проверен интеграционными тестами и настоящими формами JavaFX под тремя ролями.

## Ограничения первой поставки

Одна мастерская, одна валюта, один экземпляр backend. Ограничитель частоты запросов
находится в памяти экземпляра; для нескольких реплик потребуется общий лимитер.
Табличный CSV экспортирует текущую страницу, CSV отчёта — его отфильтрованные строки
(ограничение отчётной выборки 10 000). Desktop запускается через Maven; нативные
установщики ОС не создаются. Windows `start.cmd` объединяет запуск серверов в Docker
с подготовкой локального JDK/Maven и открытием JavaFX. Backend запускается в контейнере
без root; PostgreSQL и backend в Compose публикуются только на localhost.
